# 网站架构工作流程

当用户打开网站并执行一个操作（比如**登录**或**查询订单**）时，背后是成千上万行代码和数十个技术组件在毫秒级协同工作的结果。

我将以**用户点击“查询订单列表”按钮**这一典型业务场景为例，为你拆解一套企业级架构下**从输入到响应的完整技术工作顺序（请求生命周期）**：

---

### 🚀 第一阶段：客户端准备与 DNS 解析（浏览器端）

1. **DNS 智能解析**：浏览器检查本地缓存，若无则向 DNS 服务器发起解析。企业级架构中，DNS 会根据用户 IP 地理位置返回最近的机房 IP（智能流量调度）。
2. **HTTP/3 或 HTTPS 握手**：建立 TLS 1.3 加密通道（0-RTT 快速恢复）。此时**CDN 边缘节点**介入，若缓存了静态资源（如 `app.js`）则直接返回；动态请求则透传至源站。

---

### 🛡️ 第二阶段：边缘安全与流量接入（边界层）

3. **WAF 检测**：请求到达机房边缘，**Web 应用防火墙（WAF）** 对数据包进行规则匹配（SQL注入、XSS、恶意爬虫）。若检测到攻击，直接阻断并记录日志。
4. **四层负载均衡（LVS）**：通过 **DPDK** 等技术快速转发数据包，根据一致性哈希将请求分发到某一台 **Nginx 七层网关集群**。
5. **Nginx 反向代理**：Nginx 处理静态资源（`.js/.css/.png`）直接返回；识别到 `/api/order/list` 动态路径，则通过 `upstream` 转发给后端的 **API 网关**（如 Kong/APISIX）。

---

### 🔐 第三阶段：API 网关统一处理（网关层）

6. **身份认证（JWT/OAuth2）**：网关拦截请求，从 `Authorization` Header 中解析 **JWT Token**，调用 Redis 或远程 IAM 服务校验用户身份和 Token 有效期。
7. **限流与熔断**：网关依据 **令牌桶算法** 检查该用户/IP 的 QPS 是否超限。若触发限流，直接返回 429（Too Many Requests），防止下游服务被冲垮。
8. **路由转发与灰度标记**：网关根据请求路径 `/order` 匹配路由，转发至 **订单微服务集群**。如果请求 Header 包含 `Version: v2`，网关会将流量路由至灰度环境（金丝雀发布）。

---

### ⚙️ 第四阶段：微服务业务逻辑处理（服务层）

9. **服务注册发现（Nacos）**：订单服务在启动时已注册到 Nacos。网关转发时，通过 **服务名** 从 Nacos 获取健康的服务实例 IP 列表（如 `192.168.1.10:8080`），并负载均衡（Ribbon）选择一个节点。
10. **Dubbo/gRPC 同步调用（可选）**：订单服务本身不持有用户详细信息，它通过 **Feign 或 Dubbo** 远程调用 **用户信息微服务**，获取当前用户的等级和权限。
11. **参数校验与业务编排**：服务层使用 **Hibernate Validator** 校验入参（如页码不能为负）。随后编排业务逻辑：先查缓存，再查数据库，最后组装 VO（View Object）。

---

### 💾 第五阶段：多级缓存与数据访问（中间件与数据层）

12. **多级缓存查询（Caffeine + Redis）**：
    - 首先查询 **本地缓存（Caffeine）**，若无则查询 **分布式缓存（Redis Cluster）**。
    - 企业级场景下，Redis 采用 **读写分离 + 哨兵/集群** 模式，读 QPS 可达 10w+。缓存键通常设计为 `order:list:userId:page:1`。
13. **数据库路由（分库分表）**：若缓存未命中（Cache Miss），请求进入 **MySQL**。此时 **ShardingSphere-JDBC** 根据 `userId` 进行哈希取模，自动路由到具体的分库（如 `db_0`）和分表（如 `order_2025`）。
14. **SQL 执行与索引命中**：数据库执行 SQL，利用 **联合索引（idx_user_id_create_time）** 快速回表查询，返回原始数据。

---

### 📨 第六阶段：异步解耦与最终一致性（消息队列）

15. **非核心逻辑异步化**：查询订单列表后，服务需要记录**用户操作日志**和**埋点数据**。此时服务发送一条消息到 **RocketMQ/Kafka**（事务消息或普通异步消息），不等待 MQ 返回结果，直接释放主线程资源（异步解耦，减少 RT）。
16. **消息消费**：日志微服务消费 MQ 消息，异步写入 Elasticsearch，用于后续大数据分析。

---

### 📦 第七阶段：响应序列化与返回

17. **数据组装**：订单服务将从 DB 查询的数据和从用户服务获取的昵称、头像合并，构建统一的 **统一响应实体`（Result<T>）`**，包含状态码 `200`、`message` 和 `data`。
18. **网关日志埋点**：响应经过网关时，网关记录本次请求的总耗时（`Total RT`），并生成访问日志（Access Log）。
19. **网络传输**：数据经由 Nginx 进行 **Gzip/Brotli 压缩**（压缩率 70%+），通过 TCP 连接返回给浏览器。

---

### 🌐 第八阶段：浏览器渲染与客户端水合（前端）

20. **浏览器解析**：浏览器接收到 JSON 数据，Vue/React 框架触发 `setState` 或响应式更新。**Virtual DOM** 进行 Diff 运算，批量更新真实 DOM。
21. **静态资源 304 协商缓存**：如果页面引用的 `app.js` 未变化，浏览器从本地缓存或 CDN 读取，彻底减少带宽消耗。
22. **首屏与交互**：列表数据渲染完成，用户看到订单列表，**水合（Hydration）** 完成，页面进入可交互状态。

---

### 📊 第九阶段：全链路可观测性（贯穿始终的后台支撑）

在以上 **1~8** 的所有步骤中，三个基础设施始终在后台默默运行：

- **日志（ELK）**：每个服务节点的 `logback/log4j` 打印业务日志，Filebeat 采集后存入 Elasticsearch，Kibana 供研发检索。
- **链路追踪（SkyWalking）**：网关在请求入口生成 **TraceId**，该 ID 通过 HTTP Header 透传给所有下游服务。SkyWalking Agent 收集 Span 数据，展示完整的调用拓扑图和耗时瀑布图。
- **指标监控（Prometheus）**：每个服务暴露 `/metrics` 接口（QPS、RT、Error%）。Prometheus 定期拉取，若 `RT > 阈值` 或 `Error% > 1%`，AlertManager 触发钉钉/电话告警。

---

### 💎 总结时间线（用户视角 vs 技术视角）

| 用户感知时间    | 技术执行阶段                                   | 耗时占比 |
| :-------------- | :--------------------------------------------- | :------- |
| **0 ~ 50ms**    | DNS + TCP/TLS 握手 + WAF/LVS 转发              | 网络开销 |
| **50 ~ 150ms**  | API 网关鉴权 + 限流 + 路由                     | 网关开销 |
| **150 ~ 400ms** | 微服务业务逻辑 + RPC 调用 + 数据库查询（核心） | 业务计算 |
| **400 ~ 450ms** | 数据序列化 + Gzip 压缩 + 网络传输              | 传输耗时 |
| **450 ~ 600ms** | 浏览器解析 JSON + DOM 渲染                     | 前端渲染 |

**关键保障机制**：如果第 12 步 Redis 缓存命中，整体响应时间可从 **400ms** 骤降至 **80ms**。如果第 13 步数据库慢查询超过 1 秒，SkyWalking 会立刻捕获并告警，DBA 介入优化 SQL。
